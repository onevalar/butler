状态：**Normative Draft v2 · 手机本地轻量 Agent，正在改造**
最后更新：2026-09-26

> **阅读优先级**：§0 是最新产品方向、界面规划和实施路线，取代旧章节中“仅消耗品”“只用本地解析器”“不接云模型”的目标约束。§1–§8 保留为库存子系统规格及历史交接记录；其中数据安全、日期语义、确认、可撤销和事务约束继续有效。允许规划联网能力不等于已授权上传真实个人数据；正式接入前仍需确定上传范围、服务商和保留策略。

>
> 基础纠错版本新增：核对页逐项编辑；同名多候选明确选择；部分消耗/数量校正；已处理记录；带版本校验的撤销；三类日期分别表达、修改和清除；临期补提醒与通知点击定位。`setLotDate.date` 允许 null 表示清除，仍需字段证据和确认；`undoLot` 引用原操作 ID，只能撤销该批次最近一次数量/关闭操作，追加新事件和实际恢复值证据。关闭记录新增可选的原数量快照；旧记录没有快照时不猜测恢复数量。关闭批次仍禁止普通消耗，只有经过确认的撤销可以恢复。

本文是 Butler 2.0 的产品、领域模型和 AI 执行协议的共同事实来源。`MUST` 表示不可破坏的不变量，`SHOULD` 表示默认选择，`MAY` 表示可选扩展。旧产品说明只描述现有 MVP，不再指导新功能设计。

## 0. 新方向：理解个人生活的 Agent 管家

### 0.1 已确认的产品构想

用户通过自然语言或照片表达生活信息，不必先选择模块、填写全部字段或手动打标签。管家关联此前告知的家庭布局、物品位置、常购品牌、购买渠道、习惯和最近对话；只询问会改变结果的缺失信息。范围包括库存、食物、衣物、日程和个人安排，不把消耗品模型当作所有生活信息的固定模板。

已确认的分工：

- SwiftUI 是 iOS 主体，负责语音、拍照、对话、结果展示和必要的确认，保留原生设备能力；不改为纯 Web 壳。
- 模型通过网络接入，使用所有者的订阅登录，测试模型为 GPT-6 Sol / Medium。主模型负责理解和判断；手机内只需要一个轻量执行循环，接收工具请求、查询或修改本地记忆、返回结果，不嵌入完整编程 Agent。
- Jev 是内部 Condition Judgment（条件判断）子模型，用于相关性、实体匹配、纠正/冲突、操作语义等判断，不替代主模型。
- Agent 工具和记忆以 iPhone 本地为目标位置；订阅模型的认证与网络连接独立实现。不把 Mac 常驻服务、外部 Agent 宿主或购买云服务器设为前提。旧 `agent-host/` 是接入实验，不再作为最终架构继续扩展。
- 统一个人记忆对主模型提供一致的访问方式，但不要求所有内容使用同一种数据库；照片、精确事实和自然语言记忆可以分别保存并关联。
- 主模型可以通过工具建立定时任务；任务服务或操作系统负责到时执行，不能依赖模型持续运行。

目标例子：用户说一次“盒马的麻薯通常买小盒，放冰箱上层”，以后买同款只需补充本次变化；“现在还剩两个”更新当前数量而不是扣掉两个；“不是山姆，是盒马”纠正目标记录而非重复新增。惯常保质期和本批实际有效期分开，本批日期沿用现有可信确认规则。

### 0.2 执行与记忆边界

当前目标流程（不是已完成的真机联调）：

```text
SwiftUI 输入 → 手机内轻量执行循环 ↔ 云端主模型
                      ↕               ↕
             本地查询与修改工具     Jev 条件判断
                      ↕
             手机记忆 / 媒体 / 任务记录
                      ↓
             实际执行回执 → 对话与界面
```

- Jev 不直接持有数据库写权限。工具取出候选资料，Jev 返回判断，主模型或确定性流程使用结果，所有写入经过校验与事务。简单精确查询不必经过 Jev。
- 主模型可按需调用条件判断工具；常见判断也可在记忆检索后或写入前触发。独立问题可批量判断，依赖前一步结果的问题不能假装并行。
- 常用判断采用可测试的问题定义，候选项来自当前资料而非要求用户分类。主模型动态提出的条件属于建议，不得修改权限、确认要求或安全策略。
- Jev 的概率/置信度不是正确性或授权凭据。判断不确定、服务超时或不可用时保留原始资料并交由主模型处理，不能默默丢弃信息或阻止所有请求。
- 记忆区分当前事实、个人习惯、事件历史、原始输入/照片及来源。保留适用范围与更新时间，例如盒马小包装习惯不能覆盖山姆包装，也不能覆盖本次明确数量。
- 查询提供精简习惯摘要、最近上下文和相关当前记录；不每次遍历完整聊天。整理可在输入后异步完成，但正式保存与后台整理的状态必须分开。
- 纠正更新当前事实并保留变更来源；用户可查看、修改、删除记忆。删除应覆盖派生索引、摘要和相关缓存，不得让已删记忆从旧摘要中重新出现。
- 数量、日期、权限和重复请求由程序精确处理。相同请求重试不重复入库；旧计划不得覆盖后来的修改；模型看到的旧记录必须在执行时重新检查版本。
- UI 和对话使用同一执行回执：成功保存后才能说“已记好”；失败、待确认、执行状态未知不得冒充成功。联网断开时保留草稿，显示最后同步状态。
- 手机保存正式记录，不另外建立云端真相。查询命中和必要上下文会发给云模型，不等于资料从不离开手机。App 关闭时不能假设任意 Agent 代码能持续执行；固定提醒使用系统通知，动态后台任务另行设计。

### 0.3 新界面交互规划与首版文字入口

保留现有“青花”视觉语言和浅/深色支持。以下是功能与信息布局，不锁定最终导航样式；视觉稿和渲染验收在对应实现阶段完成。

已实现的 Debug 试用入口为“与管家聊聊 · 本机记忆试用”：原生文字对话、订阅登录、修改前后预览、确认/取消、本机记忆浏览与搜索。没有服务器地址或服务密钥表单。登录页取得设备码后打开官方授权页面，授权信息留在系统钥匙串；请求固定 GPT-6 Sol / medium。用户输入和命中的记忆发送给云模型，查询和确认保存由手机执行。当前只使用虚构资料，与原库存隔离；聊天不跨重启保留，已确认的记忆保留。以下照片、语音和任务界面仍是目标，不是已交付功能。

| 界面 | 目标交互 | 必须展示的非默认状态 |
| --- | --- | --- |
| 管家首页 / 对话 | 统一文字、按住说话、相机/相册入口；展示最近交流及今天需要关注的事项，不先选物品/衣物/日程类别 | 空白引导、录音权限拒绝、转写待发送、联网失败、可取消的处理中状态 |
| 对话结果卡 | 同一消息内呈现物品、衣物照片、日程或操作回执；可点开详情，支持纠正与适用操作的撤销 | 未保存、等待确认、已保存、部分完成、失败/重试、撤销已失效 |
| 轻量确认卡 | 只呈现影响结果的歧义，例如两盒麻薯选哪盒、核对实际有效期；已知内容不重复询问 | 无匹配、多个候选、跳过、修改值后旧确认失效 |
| 我的记忆 / 内容浏览 | 查看家中物品、照片、位置、习惯与安排；按需筛选但不强迫录入时分类；原库存列表作为一种视图继续保留 | 来源、更新时间、推断与已确认区别、纠正/删除、未同步 |
| 任务与提醒 | 查看管家安排了什么、何时触发、是否重复；可改期、暂停、取消，通知可返回对应内容 | 通知未授权、执行失败、离线、已取消、错过触发时间 |

照片卡必须引用实际保存的附件，不把生成图片冒充用户衣物。对话不能成为唯一查看入口，用户仍能直接浏览与手动纠正已有内容。

### 0.5 分步实施与验收

阶段 A–F 是新路线，不沿用旧 M0–M5 的完成标记。每步在前一步可用后扩展，已有库存功能保持可用。

**路线纠正优先于下方历史安排：**手机端本地记忆和轻量工具循环已经接入原生试用界面；`SubscriptionConnection` 负责订阅授权，`SubscriptionModel` 负责直接 HTTPS 模型请求，不要求外部 Agent 宿主。随后再扩展照片、语音和提醒。`LocalAgent.swift` 提供自然语言记忆（不要求分类）、查询、修改预览、绝对数量校正与本地确认保存。真实订阅直连已在 orb 验证查询→数量预览→回复，未运行 Codex 进程；这不等于 iPhone 上已完成真实登录和端到端使用。Mac 界面替身验证与手机真实订阅联调必须分别报告，准确结果见开发日志。

| 阶段 | 交付与依赖 | 用户能验收的效果 |
| --- | --- | --- |
| A：本地执行与模型连接 | 手机端保存记忆和执行简单工具，单独接通订阅模型认证与请求；只使用虚构资料 | 手机内查询和修改真实落盘；不需要常驻电脑。分别说明本地执行验证与真实模型连接是否完成 |
| B：第一个可信对话闭环 | SwiftUI 对话入口与库存结果卡；连接查询、购买、绝对数量校正、撤销工具，复用事务和确认层 | “买了麻薯”→“还剩两个”→“刚才说错了，三个”；界面与实际记录一致。超时重试只写一次；多盒歧义只问关键问题；日期改动重新确认 |
| C：跨会话个人记忆 | 可持久化的习惯/地点/来源、最近上下文、相关记录检索；明确购买渠道、包装与批次关系；提供记忆查看/纠正/删除 | 告诉一次盒马/山姆包装差异，重启后仍分别记得；“老地方”能引用之前位置；本次明确事实优先；删除后不再引用 |
| D：Jev 条件判断层 | 在 C 的真实候选资料上接入相关性、同物判断与纠正/冲突判断；与无 Jev 的同一主模型做对照；不改安全边界 | 测“吃了两个/剩两个”、同名不同批次、否定和改口、与旧习惯冲突、新领域请求。记录错误写入、漏掉关键记忆、追问次数、总耗时及总成本；失败可回退，只有净收益时默认开启 |
| E：媒体与第二领域 | 原始照片保存/关联、衣物内容卡；加入基础安排记录与查询，不强行套 Product/Lot；多模态上传另按已同意范围执行 | 拍衣物后下次能查看同一照片；能问“最近几天有什么安排”；同一对话自然切换库存、衣物与日程，无需手工分类 |
| F：主动任务与真机试用 | 区分固定提醒和到时调用 Agent 的任务；确定云端调度/推送或受限本地方案；引入天气等获准的数据源 | “明早提醒我”可改期取消；“明早按天气推荐衣服”到时使用新天气与现有衣物。App 关闭、跨时区、网络中断与重试不重复执行；真机检查通知跳转与权限拒绝 |

实施补充要求：

- 在任何真实库迁移或引入新正式存储之前，先完成可恢复备份和临时副本迁移验证；不删除原库，不以模型试验改变原数据。
- 试验采用虚构数据和独立存储；真实数据上传、共享云部署和发布各自需要明确授权。应用包内不放服务商共享 API 密钥；使用受保护的服务端凭证代理或明确的个人密钥方案。
- A 阶段可同时用小型独立实验验证 Jev，不必等 D 才申请；D 表示接入正式闭环的顺序，不是取消已确认的子模型分工。
- “一盒几个”是包装与内容物数量关系，现有整数单位模型尚不完整支持；B/C 必须明确记录单位，不能把吃掉两个麻薯当作扣掉两盒。
- 每阶段同时测试容易混淆的反例和失败恢复；涉及 UI 时验收浅/深色、确认/失败/离线等实际渲染状态。正式发布前补齐真机验证和数据兼容检查。

### 0.6 需要所有者协助的条件

1. A 阶段：所有者已同意使用 Codex Agent 的订阅登录与额度进行开发验证，不再要求另购 Platform API 额度或重复确认这一选型。正式连接、套餐可用模型、调用限额与上传范围仍需核实；凭证通过安全配置或官方登录输入，不贴在聊天或提交到仓库。
2. A/D 阶段：所有者已确认具有 Jev 访问资格；尚未配置或验证本项目连接，也未确认账号免费额度和付费上限。测试预算指额外按量调用/托管费用的上限，不是订阅费；未获同意不自动充值、切换付费 API 或租用服务器。
3. B/C 阶段：提供少量脱敏的日常说法及期望结果，特别是改口、包装数量、家中位置；不需要整理完整物品表或设计标签。
4. 选定云端执行后：协助确定托管账号、地区、预算、备份/保留/删除要求；未经确认不部署。若选本地 Agent，明确 App 关闭时哪些任务不可执行。
5. F/发布阶段：提供真机、通知权限和必要 Apple 签名/推送能力，参与语音、照片与通知真实体验验收。

订阅接入调查（2026-09-26）：[官方 App Server 文档](https://developers.openai.com/codex/app-server)提供嵌入自有产品的会话、工具和 ChatGPT 托管登录接口，包括浏览器与设备码登录；这条路线嵌入的是 Codex Agent，不是把订阅凭证变成通用 OpenAI API key。可先在用户控制的 Mac 上验证，再由 SwiftUI 客户端通过受保护的连接访问；这是待验证建议，不是已决定部署。官方当前将 app-server 命令及 WebSocket 路线标为实验性/不支持生产工作负载，不能直接承诺正式发布可用。长期无人值守任务与公开多用户分发需另核实适用支持与条款，不把个人订阅当作共享后端额度。订阅额度不足时应提示并暂停，不自动转付费。

## 1. 产品定义

Butler 是一个 AI Native 的个人物品与生活资产管理助手。它通过语音、文字、图片、订单等输入理解用户拥有的物品，将信息整理成可信、可持续更新的个人物品网络，并围绕过期、消耗、复购和生活决策提供主动服务。

### 1.1 第一阶段范围

第一阶段只服务具有数量、消耗、保质期或复购需求的消耗品：

- 食品和饮料；
- 药品；
- 洗护用品；
- 家庭日用品。

第一阶段 MUST 完成“低成本录入 → 可信确认 → 风险分诊 → 行动 → 历史学习”闭环。

### 1.2 第一阶段非目标

- 不实现衣物搭配、数码资产和保修管理；
- 不实现家庭账号与多人同步；
- 不绑定特定云模型供应商；
- 不以图数据库作为前置条件；
- 不允许大模型直接读写持久化数据库；
- 不以 Widget、Siri 或订单平台接入替代核心闭环。

### 1.3 产品原则

1. 用户说一次，系统尽量完成。
2. 只追问真正重要且无法可靠推断的信息。
3. 推断必须可见、可解释、可纠正。
4. 食品、药品和真实包装日期宁可确认，不可编造。
5. 大模型负责理解和规划，规则负责校验，事务服务负责执行。
6. 每次纠正都应让同类输入下次更省事。
7. 提醒必须连接到可执行行动。
8. 底层支持长期扩展，首发体验保持聚焦。

## 2. 核心成功指标

北极星指标：**每周由 Butler 帮助用户及时处理、正确补货或避免浪费的物品数量。**

阶段指标：

- 从开始输入到完成入库的中位时间；
- 一次表达成功录入的物品比例；
- 每件物品平均追问次数；
- 常购商品零追问完成率；
- AI 字段纠正率和错误自动执行率；
- 包装日期识别准确率；
- 临期提醒后的处理率；
- 过期丢弃率和重复购买减少率；
- 用户纠正后同类错误的复发率。

## 3. 领域模型

### 3.1 CatalogProduct：产品档案

回答“这是什么”。它保存品牌、规格、类别、条码、通常保质期等可复用身份信息。

产品 MUST NOT 保存用户拥有的数量、购买时间、批次到期日或消费状态。同名和同条码记录在第一阶段 MAY 共存，系统只能建议合并，不能自动合并。

### 3.2 InventoryLot：库存批次

回答“用户拥有的是哪一批”。不同购买时间或到期日期的同一产品 MUST 使用不同批次。

第一阶段数量按完整包装单位使用整数记录，例如 3 瓶、2 盒。分数、克、毫升和单位换算是下一阶段明确决策；不得用负数或浮点误差模拟。

批次状态：

```text
active ──用尽──▶ depleted
   ├────丢弃──▶ discarded
   ├────转赠──▶ gifted
   └────归档──▶ archived
```

不变量：

- 新建活跃批次数量 MUST 大于 0；
- 数量 MUST NOT 小于 0；
- 关闭后的批次不能接受普通消耗操作；
- 批次必须引用一个已存在的产品；
- 删除或归档产品不得级联删除批次、证据和事件。

### 3.3 三类日期

日期语义 MUST 分离：

1. `packageExpiryDate`：包装、订单或用户明确给出的真实有效期；
2. `estimatedExpiryDate`：规则或模型根据产品和储存方式估算的日期；
3. `plannedUseByDate`：用户希望在此之前使用的个人管理目标。

系统估算值 MUST NOT 写入包装有效期。计划使用日期 MUST NOT 被显示为食品安全结论。非用户直接填写的日期 MUST 具备字段证据。

仅有月份或存在日/月歧义的包装日期不得静默伪造精确日期；在日期精度模型落地前必须进入确认流程。

### 3.4 PersonalProductTemplate：个人模板

保存常购产品的建议值：通常购买数量、单位、储存位置、消费周期、提醒提前量和复购阈值。

模板是默认策略，不是产品或批次的客观事实。模板自动学习尚未启用；第一阶段只能由用户明确确认或编辑后更新。

### 3.5 FieldEvidence：字段证据

证据按字段记录，因为名称、数量、分类和日期可能来自不同输入。

来源枚举：

- `userStated`：用户本次明确表达；
- `userEdited`：用户手动修改；
- `ocr`：包装图片识别；
- `orderImport`：订单或小票；
- `heuristicParser`：本地启发式解析；
- `modelInference`：大模型推断；
- `habitInference`：个人习惯推断；
- `systemEstimate`：确定性规则估算；
- `legacyUnknown`：旧数据来源无法证明。

确认状态与来源必须独立：`unverified`、`userConfirmed`、`rejected`。

不变量：

- 置信度 MUST 是有限的 `0...1` 数字；
- AI、OCR 或规则不得自行标记为 `userConfirmed`；
- AI 计划的证据结构不包含确认状态或确认凭据；M0 只生成绑定操作、实体、字段、值和 revision 的确认要求；
- M1 的确认凭据必须由可信 UI/直接命令边界单独提供，不能作为模型输出的一部分；
- 确认凭据 MUST 同时绑定 plan、operation、entity、field、proposed value 和 expected revision；任一值变化后旧凭据失效；
- AI 计划中每个会被持久化的业务字段 MUST 提供对应字段证据；
- 用户纠正必须追加新证据，不得篡改历史证据；
- 接受的 AI 字段必须能够追溯到操作和证据；
- 旧数据无法证明来源时只能使用 `legacyUnknown`。

### 3.6 InventoryEvent：事件历史

事件记录购买、入库、移动、数量调整、用尽、丢弃、转赠、纠正和模板更新。产品与批次保存当前可查询状态；事件是不可变审计历史，不是唯一状态来源。

不变量：

- 每个语义操作必须拥有稳定 `operationID`；
- 同一 `operationID` 重放必须是幂等操作；
- 当前状态修改与事件追加必须在一次 `ModelContext.save()` 中完成；
- 事件通过仓储 API 只追加，不原地修改；
- 修改现有实体必须带 `expectedRevision`，防止旧 AI 计划覆盖新数据。

### 3.7 LegacyItemLink：旧数据映射

记录旧 `Item` 与新 Product/Lot 的一一迁移关系，保证迁移可重复执行且不产生重复记录。

## 4. AI 输入与执行边界

统一输入管线：

```text
语音 / 文字 / 图片 / OCR / 订单
            ↓
      多模态理解与实体提取
            ↓
      InventoryOperationPlan
            ↓
  实体匹配、规则校验、风险策略
            ↓
 自动执行 / 轻量确认 / 精确追问 / 拒绝
            ↓
     事务写入 + 证据 + 事件
```

### 4.1 Operation Plan

`InventoryOperationPlan.schemaVersion` 当前为 `1`。计划包含：

- `planID`：本次规划标识；
- `inputID`：原始输入标识；
- `operations`：白名单结构化操作；
- `unresolvedFields`：模型不能可靠补全的字段。

支持的第一版操作：

- `createProduct`
- `addLot`
- `adjustQuantity`
- `setLotDate`
- `moveLot`
- `closeLot`
- `createTemplate`
- `updateTemplate`

编码采用显式判别结构：

```json
{
  "operationID": "UUID",
  "operation": {
    "type": "addLot",
    "payload": {
      "lotID": "UUID",
      "productID": "UUID",
      "quantity": 3,
      "unit": "包",
      "packageExpiryDate": null,
      "estimatedExpiryDate": null,
      "plannedUseByDate": "2026-10-26T00:00:00Z",
      "storageLocation": "常温",
      "evidence": [
        {"fieldKey":"quantity","source":"userStated","confidence":1.0,"rawText":"三包"},
        {"fieldKey":"unit","source":"userStated","confidence":1.0,"rawText":"包"},
        {"fieldKey":"plannedUseByDate","source":"systemEstimate","confidence":0.8,"rawText":null},
        {"fieldKey":"storageLocation","source":"modelInference","confidence":0.8,"rawText":null}
      ]
    }
  }
}
```

Schema v1 的 JSON 日期 MUST 使用 `InventoryOperationCoding` 提供的 ISO-8601 编解码器；调用方不得使用 `Date` 的默认数字编码。模型不得输出任意数据库字段名或 SQL。未知协议版本、未知操作类型和结构非法的计划必须拒绝。

### 4.2 策略决策

策略输出只有：

- `execute`：低风险、结构完整且来源合格；
- `requiresClarification`：必填字段没有候选值，需要向用户精确追问，不能伪装成确认；
- `requiresConfirmation`：返回精确到 operation、entity、field、proposed value 和 revision 的确认要求；
- `reject`：违反数据或安全不变量。

单一置信度阈值不得直接授权写入。自动执行必须同时满足：

1. 操作属于低风险白名单；
2. 所有字段结构有效；
3. 字段来源符合要求；
4. 没有未解决的必填字段；
5. 修改操作的 revision 前置条件成立；
6. 没有食品、药品或身份合并风险。

包装有效期、药品安全字段、销毁操作、产品合并和身份修改，无论模型置信度多高都必须确认。

### 4.3 对话行为

系统 SHOULD 一次完成可确定部分，只询问会改变结果的关键歧义。例如“冰激凌放冰箱”必须确认是冷冻还是冷藏；方便面没有包装日期时可以设置个人计划使用日期，但不能制造包装有效期。

查询型回答必须来自结构化数据检索，大模型不得根据对话记忆猜测库存。执行型回答必须先形成操作计划，再经过策略和事务层。

## 5. 兼容与迁移策略

### 5.1 基础版本（当前里程碑）

- 保留 `Item` 的所有持久化字段、枚举值和行为；
- 新增空的 V2 实体表；
- 现有界面继续只读写 `Item`；
- 不回填、不双写、不自动合并；
- 不移动数据库位置；
- 容器打开失败时不得删除或静默重建数据库。

此版本需要证明旧数据库可以轻量升级且所有旧 `Item` 字段保持不变。

### 5.2 旧数据导入版本

后续迁移必须显式、幂等并可审计：

1. 查询没有 `LegacyItemLink` 的旧记录；
2. 保守地为每条旧 Item 创建一个 Product 和一个 Lot；
3. 同一事务创建映射和 `legacyImported` 事件；
4. 不按名称自动合并产品；
5. 无法证明的来源标记为 `legacyUnknown`；
6. 在 V2 读取路径验证完成前继续保留旧 Item。

旧字段 `isEstimated == false` 不等于用户确认，因为旧解析器会把启发式日期写成非估算日期。

### 5.3 暂时禁止的实现

- 替换、重命名或删除 `Item`；
- 在普通启动流程中回填 V2 数据；
- 从旧 `DataManager` 同时双写 Item 和 V2；
- 自动合并同名产品；
- 把旧日期自动标记为已确认包装日期；
- 新增必填 SwiftData 关系或级联删除；
- 让 LLM 直接访问 `ModelContext`；
- 同时进行 App Group 迁移、Widget 接入和数据模式迁移。

## 6. 里程碑与验收标准

### M0：可执行规格与兼容基础层

交付：本文、V2 空模型、统一 Schema、Operation Plan 和只验证不执行的 Policy。

验收：

- 现有界面和业务代码保持使用 `Item`；
- 新安装能创建完整 Schema；
- 旧 Schema 数据库能原地打开；
- 所有旧 Item 行和字段完全保留；
- V2 表为空；
- 未知协议版本、负数量、非法置信度被拒绝；
- 包装有效期和销毁操作要求确认。

### M1：旧数据安全导入与 V2 仓储

交付：迁移器、事务化仓储、事件幂等、revision 校验和迁移测试。

源码状态：仓储与显式迁移器已实现，但不会在应用启动时运行；完成 macOS/Xcode 旧库迁移测试前不得接入发布流程。

验收：

- 重复迁移不产生重复记录；
- 每条旧 Item 有完整映射；
- 状态修改、证据和事件原子保存；
- 持久化错误向上传递，不使用 `try?` 吞错；
- 不自动合并产品或伪造来源。

### M2：AI Native 录入闭环

交付：统一语音/文字输入、结构化计划、产品匹配、确认卡和精确追问。

验收示例：一句话录入牛奶、方便面和冰激凌，正确创建三个产品/批次；只对冰激凌储存位置等关键歧义追问；方便面的个人计划日期不得写成包装日期。

源码状态：已实现隔离于 Release 的 M2 调试闭环，包括本地受限中文规划器、冻结计划修订、同名产品显式选择、最终审核和事务写入。调试入口使用独立内存库，不接触正常数据库。当前本地规划器用于验证协议和交互边界，不代表最终云端模型能力；macOS/Xcode 验证完成前不得启用生产入口。

### M3：风险分诊与行动

交付：统一待确认中心、分层风险、批次优先级、通知摘要和通知快捷操作。

### M4：学习与复购

交付：用户确认的个人模板、快速复购、消费周期、补货建议和浪费洞察。

### M5：多模态和外部数据

交付：图片、条码、小票和订单候选导入。外部数据默认生成待确认候选，不直接污染正式库存。

## 7. 已确认的阶段决策

产品所有者于 2026-07-26 确认：

1. M1 使用完整包装整数；克、毫升和半瓶等分数留待后续版本；
2. 普通移除保留历史，另设明确的永久抹除操作；
3. 模糊包装日期保留原精度，不伪造具体日，安全敏感物品要求确认；
4. 第一阶段产品合并始终由用户确认；
5. 药品采用严格模式，不进入普通低风险自动执行白名单；
6. 接入云模型前单独确认上传范围、授权方式和保留策略；当前不上传库存、语音、图片或订单。

产品所有者于 2026-09-22 追加确认：

7. 旧 `Item` 数据系统不再需要，正常界面直接读写 V2（Product / Lot / Evidence / Event）。本条取代 §5 的“基础版本/旧数据导入”约束和 §8.7 的生产启用门禁：不做旧数据迁移、不双写；`Item` 仅为让既有本地数据库能正常打开而保留在 Schema 中，界面不再读取。所有写入仍经 `InventoryPolicy` 与 `InventoryRepository`，界面按钮点击即可信确认边界。
8. 界面采用“青花”设计方向（Paper 文件 butler），浅色与深色两套配色同时支持。

产品所有者于 2026-09-23 追加确认：

9. 本地解析器承担“听懂日常说法”，不依赖 Apple 智能或云端模型。再次购买且家里只有一个同名产品时自动归到该产品，由核对页展示并可一键改为新产品；有多个同名产品时仍需追问。
10. 散装蔬果没有包装日期可读，系统按常见保鲜时长给出“计划吃完”建议（标为系统估算），不再要求拍包装；包装生鲜与药品仍不猜测任何日期。

## 8. macOS/Xcode 验证与发布门禁

### 8.1 当前进度基线

截至 2026-07-26：

- M0 的规格、V2 additive Schema、Operation Plan 和 Policy 源码已完成；
- M1 的事务仓储和显式、幂等旧数据迁移器源码已完成，但没有生产调用点；
- M2 的文字/本地语音入口、受限本地规划器、冻结计划追问、同名产品选择、最终审核和事务写入已形成 Debug-only 闭环；
- 正常启动仍只运行旧 `Item`、`DataManager` 和 Dashboard；没有回填、双写、自动合并、云端上传或生产 V2 写入口；
- 已完成 Debian orb 可执行的静态检查、生命周期脚本检查、真实中文验收句拆分检查和源码安全复核；
- 尚未完成任何 Apple SDK 编译、SwiftData 迁移测试、模拟器/真机测试或 UI 回归，因此 M0–M2 当前状态是“源码完成，发布验证未完成”。

当前 Xcode 工程只有 `Butler` 应用 Target，没有测试 Target。必须在 macOS、Xcode 26.2 和 iOS 26.2 SDK 环境新增 `ButlerTests`，但不得为了测试而接通 Release 的 V2 写路径。

### 8.2 编译与工程检查

- Debug 和 Release 均完整编译 Butler scheme；
- 验证 SwiftData `@Model`、`#Predicate`、`@Attribute(.unique)` 和完整 Schema 的宏展开；
- 验证 `@Observable`、`@Bindable`、`@Query`、MainActor 和异步语音调用没有隔离或生命周期错误；
- 确认 Release 不包含 `--m2-input-harness` 可达入口，M2 执行协调器、本地规划器和 V2 输入 UI 被条件编译排除；
- 确认签名、权限描述和 App Group 配置可以打开既有数据库；本阶段不得顺便迁移数据库位置或接入 Widget 数据共享。

### 8.3 M0 Schema 兼容测试

必须在临时路径使用旧版 `Item`-only Schema 创建数据库并写入固定夹具，再用 `ButlerStore.schema` 打开同一文件。夹具至少覆盖：

- 活跃、待补全、已消耗和已丢弃状态；
- 已消耗但数量仍为正以及数量为零；
- 无日期、旧版估算日期和旧版非估算日期；
- 重复名称、不同单位、自定义单位、备注和创建时间；
- 所有旧枚举 raw value 和可选字段组合。

验收要求：升级前后逐行、逐字段相等；旧 `Item` 数量不变；V2 表初始为空；新安装可以创建、保存、关闭并重新打开完整 Schema。还必须注入一次打开或迁移失败，证明应用不会删除、覆盖或静默重建用户数据库。

### 8.4 M1 仓储与迁移测试

`InventoryRepository` 必须覆盖：

- 一个计划中的所有操作、证据和事件只在一次 save 中原子提交，中途错误全部回滚；
- 相同 operation ID 和相同 payload 安全重放，不重复改变状态；相同 ID、不同 payload/subject/type 必须冲突；
- stale revision、缺失实体、归档产品、非法状态、重复实体和整数溢出均明确失败；
- 包装有效期、现有状态修改和销毁操作没有匹配确认回执时拒绝执行；回执必须精确绑定 plan、operation、entity、field、value 和 revision；
- 每个持久化业务字段都有正确 source、confidence、value 和 verification state，事件 payload 可重放审计；
- 模板的 product 唯一性、revision 和更新原子性成立。

`LegacyItemMigrator` 必须覆盖：

- 只能显式调用，普通冷启动和 Release 路径不会自动运行；
- 第一次为每个未迁移 Item 创建一个 Product、一个 Lot、一个 Link 和审计记录，第二次运行不新增任何记录；
- 不按名称合并重复 Item，不把旧日期提升为已确认包装日期；
- 原始 Item 快照可审计，旧来源保持 `legacyUnknown`，旧日期只进入未验证估算字段；
- 任一行失败时事务回滚，不留下半迁移 Link 或孤立实体。

### 8.5 M2 Debug 闭环测试

在 Debug scheme 增加启动参数 `--m2-input-harness`，使用默认句子：

> 我今天买了一瓶牛奶、三包方便面和一个冰激凌。冰激凌先放冰箱了还没吃。

必须验证：

- 计划恰好包含三个产品和三个批次，数量与单位正确；
- 只对冰激凌提出冷藏/冷冻追问，答案修订冻结计划而不重新运行 Provider，所有既有 ID 保持不变；
- 方便面获得从参考日期按日历增加三个月的 `plannedUseByDate`，`packageExpiryDate` 保持为空；
- 最终审核展示产品身份、新建/已有状态、数量、日期、储存位置、证据和高风险确认项；
- `.execute` 只表示允许进入审核，未点击最终确认不得写入；确认要求变化时旧回执不能继续使用；
- 同名产品只产生只读候选，任意非候选 ID 被拒绝，选择已有产品只重连目标批次，选择独立产品不会合并；
- 调试入口使用内存库；关闭后正常启动时正式数据库没有新增 V2 数据；
- Release 构建无法进入 Harness，也不存在普通 UI 到 V2 Repository 的写入链路。

### 8.6 模拟器、真机与旧功能回归

- 模拟器和真机分别验证麦克风与语音权限；M2 无本地中文识别能力时明确提示改用文字，不静默上传；旧流程仍保持本地优先、不可用时服务器识别回退；
- 验证新安装冷启动、旧数据库冷启动、前后台切换和异常退出后重启；
- 回归 Dashboard、详情、消费、丢弃、日期补全、通知和 Spotlight，确认仍只读写 `Item`；
- 验证最低支持系统上的旧库升级，并确认失败不会删除或重建数据；
- 云模型、语音、图片、订单或库存上传不属于本轮验证，必须等待独立隐私策略确认。

### 8.7 生产启用条件

以下条件全部满足前，M0–M2 不得标记为可发布，也不得打开生产 V2 写入口：

1. 8.2–8.6 的测试全部通过并在 `DEVELOPMENT_LOG.md` 记录 Xcode 版本、设备/模拟器、结果和失败修复；
2. Dashboard 与详情具备经过验证的 V2 读取路径，新写入批次不会在正常界面不可见；
3. 旧数据迁移有显式用户/开发入口、进度、失败恢复和审计展示；
4. 保留旧 `Item`，直到迁移、读取、编辑、通知和 Spotlight 达到功能等价；
5. 不采用 Item/V2 双写作为过渡方案。

Debian Amp orb 无法提供 Apple SDK，因此只能完成源码和静态验证，不能替代以上发布门禁。
