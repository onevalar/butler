# 页面上下文对话、灵活任务与输入框

日期：2026-09-28。本次实现建立在 `8f1c3b9` 之后的工作区代码上；安装包和 TestFlight 不会随源码自动更新。

## 已接入的行为

| 入口 | 打开的会话 |
|---|---|
| 首页、概览、任务列表 | 通用对话 |
| 家里物品列表 | 库存对话 |
| 具体物品批次 | 该批次的独立对话，用稳定 ID 识别，改名不丢历史 |
| 具体任务 | 该任务的独立对话，完成、取消后保留 |
| 管家与设置及其子页面 | 设置对话 |
| 某天的日程 | 该日期的独立对话 |

对话标题显示正在讨论的对象，菜单可切回通用对话或设置对话。各会话的历史、摘要、草稿、照片、待确认提议和运行请求独立；账号、库存、笔记、任务与全局设置共享。每轮读取最新对象事实，旧聊天中的数量与规则不能替代当前数据。长按水晶球在开始录音时固定目标会话。

物品、任务详情提供「相关对话」。其他会话中明确查询或修改该对象的轮次以引用方式出现，仍可打开来源对话；新建物品确认后绑定真实批次 ID。全量库存预取不会把所有物品都挂到当前轮次，只有原话明确提及名称的返回记录会建立关联。旧聊天整体保留为通用历史，不猜测拆分。管家日记聚合所有会话。

新增工具提供当前上下文、任务读取、分阶段计划、任务完成/暂停/恢复/取消，以及允许修改的设置。AI 修改沿用「提议 → 用户确认 → 本机执行与回执」；工具不会自行确认。设置包括外观、到期提醒提前天数/时刻、Jev 与预取开关、系统日历显示、家庭背景，不能读写密钥或替用户授予系统权限。设置发生并发变化时旧提议失效。

首页新增「任务与历史」入口。任务可组合一次、每日、每周、每隔若干分钟、各阶段起止及次数上限；可以指定提醒截止，或明确要求某时自动标记整个任务完成。修改保留任务 ID 并提高版本，旧通知不能修改新规则；完成、暂停、取消会撤销后续计划和关联的稍后提醒。各阶段按自身边界计算并合并，同一时刻去重，不隐含“下一阶段自动截断上一阶段”。

任务详情显示状态、规则预览、真实活动记录及调度警告。聊天提议列各阶段规则与近期时间点；确认后报告未排完、权限关闭或安排失败。语音输入采用左侧加号、右侧外置麦克风/发送；有文字或照片时框内保留无底色线性麦克风。按钮听写停止后先保留草稿，长按水晶球仍沿用松开发送；录音期间暂锁手动编辑，收尾完成后可修改。权限拒绝、中断、关闭和切换会话都会结束录音并保留已收到的文字。

备份格式升级到 v2，覆盖旧通用历史、新会话、摘要、草稿、照片、任务及受支持配置。旧备份仍可读取；路径校验、损坏文件保护和恢复后的缓存刷新一起覆盖。原历史不再只保存最近 2000 轮。

## 当前边界与体验方法

- 高频间隔必须有次数或截止；普通每日/每周在起始时间允许时用系统重复。复杂计划由本机预排近期通知，本应用为任务设置 40 条待发预算（不是对 iOS 上限的断言）。超额会显示覆盖范围与补排提示，不能承诺长期不打开 App 仍执行无限复杂计划。
- 到提醒截止不会自动把事情当成完成。只有显式 `autoCompleteAt` 才自动完成整个任务；通知已提前截断，前台计时或下次回到 App 时更新持久状态。未实现每次重复的独立完成实例。
- 支持的是已实现能力的组合。外部状态触发、服务器执行、任意脚本、任意新增软件能力、自动撤销设置、完整规则版本差异浏览，仍需后续开发。
- 保留全部历史不等于无限规模优化；目前按会话文件保存，对话工具可分页读取，跨会话列表尚未做大规模索引。
- 可在首页、物品页和设置页分别输入草稿再切换，检查标题和草稿独立；在物品页查看相关对话。在设置对话说“把到期提前提醒改为 3 天”，确认后核对原设置控件。
- 可说“连续三天提醒寄件，前两天每天 20 点，第三天 18 点起每十分钟一次，最多六次；完成就停止”。核对提议的实际日期、时区、阶段截止和六次时间后确认，再从任务详情暂停、修改或完成。
- 输入空白、文字、仅照片，分别检查外侧按钮和内侧线性麦克风；开始听写后停止，确认文字保留且没有自动发送。

以下为实施前保存的设计推导。含“建议”的内容需与上面的实现范围区分，不能据此认定全部已完成。

## 1. 用户目标

- 大多数页面的水晶球都能打开 AI，但默认上下文和历史与入口相关。
- 首页是通用对话；物品和任务拥有可回顾的讨论及操作历史；设置页可以通过 AI 修改已提供的配置。
- 用自然语言表达复杂任务，支持多阶段、重复、暂停、结束、完成及后续修改，不必为每种组合设计固定表单。
- 输入区左侧保留功能按钮；右侧外置独立语音按钮。有可发送内容时外侧变发送按钮，输入框内部右侧保留无填充背景的线性语音图标。

## 2. 实施前代码事实（`8f1c3b9`）

- `ContentView` 只持有一个 `ButlerChat`；`ChatRequest` 只有打开方式，没有入口对象上下文。
- 聊天与摘要为全局存储，草稿使用全局键；`ChatTurn` 的回执是文字，没有关联实体和操作编号。保存只保留最近 2000 轮，不能据此承诺完整永久历史。
- 库存已有独立的 `InventoryEvent`，可以作为实际操作历史基础。聊天内容不等于操作已经执行。
- `TimedReminder` 只有一次、每日、每周；没有独立任务完成状态、结束条件、分阶段策略或修改提醒工具。
- 通知注册了“完成”动作，但处理分支没有实现对应逻辑。贪睡通知使用随机编号，取消原提醒也不能统一取消这些衍生通知。
- `ReminderStore.add` 会过滤已到点的一次性提醒，现有存储不适合承载长期任务历史。
- 设置界面已有多种配置，但尚未提供读取/修改设置的模型工具。
- 输入框已有空白时麦克风、可发送时箭头、听写/模型运行时停止的切换；按钮目前在框内。已有听写可接续草稿，但文本增量直接写回草稿，扩展交互时要防止覆盖用户编辑。

## 3. 对话属于对象，页面决定默认入口

建议采用稳定对象 ID，而不是页面标题作为会话标识。

| 入口 | 默认对话 | 初始上下文 |
|---|---|---|
| 首页 | 通用会话 | 当前日期、总体能力；需要时再查资料 |
| 物品 | 对应商品/批次会话 | 名称、单位、状态、必要的最新库存及关联记录 |
| 任务 | 对应任务会话 | 目标、当前规则、状态、最近变更、关联对象 |
| 设置 | 设置会话 | 可修改配置的定义和当前值；不注入密钥 |
| 筛选列表/某天 | 通用或该类工作区会话，附本次视图范围 | 日期、筛选条件、选择项；不无限创建临时会话 |

上下文是默认理解范围，不是禁止跨对象查询。例如从火腿页面问晚餐，仍可查其他食材和偏好。跨对象修改必须明确实际对象，不得因为入口不同就把“这个”误指向别的记录。

同一对象从通知、列表、首页链接进入，都应打开同一对象历史。商品总览与某一购买批次需要明确区分：物品页的会话可查看相关批次，具体批次详情默认聚焦该批次。

建议会话标题显示“正在讨论：火腿／寄件任务／设置”，并能切换通用会话或查阅历史。草稿、附件、滚动位置、待确认操作和运行中的请求按会话隔离，避免关闭一个页面后把内容发送到另一个对象。

打开会话时刷新对象事实，历史对话只用于理解过去；旧数量或旧规则不能覆盖当前数据库。改名不换会话；完成或归档保留历史。对象删除后显示历史对象状态，禁止旧卡片重新写入不存在的对象，保留与删除策略需要明确。

旧全局对话迁移为“通用历史”，不凭模型猜测批量拆分。以后从通用会话涉及物品/任务时，为该轮添加对象关联；对象页显示原消息引用及来源，不复制出多个相互矛盾的消息副本。是否把新建任务的后续对话切换至任务会话，应给予清晰入口，不悄悄搬走原对话。

## 4. “聊过什么”和“实际做过什么”都能回看

同一对象应提供两种互相关联的记录：

- 对话：用户原话、模型回复、解释和未执行提议。
- 活动：真实创建、修改、确认、取消、完成、规则调度结果等事件。

消息、提议、执行回执和事件通过会话/轮次/操作 ID 关联。不能把 AI 说“已完成”当成执行成功；不能把“通知已安排”当成“用户已收到”。长历史采用分页/归档和按需检索，摘要不能替代原始记录。数据规模、备份与用户删除也必须覆盖新增存储。

## 5. 用可组合的能力支持未知组合

核心流程：用户自然语言 → AI 读取当前对象与所需能力 → 生成结构化规则或变更 → 程序校验、解释和预览 → 按权限执行 → 保存真实回执。

不必枚举每种用户句式，但必须实现底层能执行的能力。模型可以组合已有工具，不能凭对话创造系统权限、外部接口或未开发的功能。新的能力可以注册后向模型提供说明，按当前上下文优先暴露相关工具，并允许发现额外能力。

建议逐步提供任务读取、创建、修改策略、暂停、恢复、完成、取消、试算后续执行时间，以及设置读取、修改和恢复能力。每项修改要有参数范围、合法值、可用性和一致的执行回执。

AI 负责理解和规划，规则引擎负责执行已确认的计划。不能每几分钟都唤醒大模型临时重新决定是否提醒。Jev 不是调度器，也无需成为每次规则执行的必经环节。

普通、可逆的配置修改可直接应用并显示撤销；复杂提醒首次创建或大幅修改，先给自然语言摘要与下一批时间点预览，再一次确认。密码、授权和系统权限通过适当的系统入口处理，不交给普通设置工具任意写入。明确执行失败与规则保存成功但调度失败的不同状态。

## 6. 任务、提醒策略和提醒实例分开

建议数据结构至少包含：

- 任务：稳定 ID、目标、关联对象、状态（进行中/暂停/完成/取消/到期关闭等）。
- 策略：开始和结束时间、时区、重复周期、不同阶段、例外、重复次数或窗口、完成与停止条件。
- 提醒实例：由策略生成的具体通知、所属任务/阶段/策略版本、计划时间和调度结果。
- 活动：创建、修改、推迟、完成和执行失败等可回溯事件。

例如用户确定“连续三天提醒寄件，前两天每天 20:00，第三天 18:00 起每十分钟一次，最多六次；我完成就停止”，程序可以组合阶段和次数，不需要新增一张专用表单。若用户只说“最后一天每隔几分钟提醒几次”，应补清会影响执行的参数或展示明确默认值，不能无声猜成无限催促。

“提醒到期停止”与“事情已经完成”不同。用户明确要求某时自动标记完成时，保存为一种状态规则，并说明这不证明现实中的事情已做。重复任务还应区分“本次完成”和“以后都结束”。

修改规则时：保留任务 ID，递增策略版本，统一撤销旧的后续通知和贪睡实例，安排新计划，记录差异。旧版本通知的动作不能误改新计划；完成动作须幂等。到期/完成规则要在读取和执行入口核对，防止界面重开后继续显示过时状态。

要覆盖跨午夜、旅行时区、夏令时、日期不存在、重复触发、离线、重启、通知权限变化及多个任务争用通知容量。规则本身合法与系统通知是否成功安排要分别验证。

## 7. iOS 执行边界

普通本地通知可预先交给系统，但后台任务不保证在指定时刻启动，不能依赖 App 每隔几分钟运行一次代码维持复杂日程。Apple 也不保证通知必然按时送达。

有限时间窗口和有限次数的复杂提醒可预先展开；简单周期可使用系统重复机制。长时间多阶段计划需要考虑系统待发送容量和补排机会，不能未经验证就承诺“无限期不打开 App 也能执行任意规则”。

需要持续读取外部状态、长周期复杂调度或跨设备自动化时，可评估服务器执行及推送；服务器也不能保证绕过关闭通知、设备离线等因素。首阶段不以引入常驻云服务为默认前提，而应明确每类任务已验证的支持范围。

官方依据：
- [本地通知安排](https://developer.apple.com/documentation/usernotifications/scheduling-a-notification-locally-from-your-app)
- [后台任务时间不保证](https://developer.apple.com/documentation/backgroundtasks/bgtaskrequest/earliestbegindate)
- [通知响应和自定义动作](https://developer.apple.com/documentation/usernotifications/handling-notifications-and-notification-related-actions)
- [User Notifications 与投递限制](https://developer.apple.com/documentation/usernotifications)

## 8. 输入框交互建议

基础布局：左侧独立加号，中间多行输入框，右侧独立主动作按钮。输入框内部麦克风使用线性图标、无填充底色，但仍保留足够点击区域和可访问标签。

| 状态 | 外侧右按钮 | 框内右侧 | 行为 |
|---|---|---|---|
| 无可发送内容 | 麦克风 | 无 | 点击开始听写 |
| 有文字或附件 | 发送 | 线性麦克风 | 允许继续用语音补充 |
| 语音准备中 | 可取消的准备状态 | 避免重复入口 | 防重复启动，不丢现有草稿 |
| 正在听写 | 停止听写 | 录音状态提示 | 停止后保留文字，默认不自动发送 |
| 听写收尾 | 短暂处理中 | 状态提示 | 收齐最后一句再允许发送，防丢尾字 |
| 模型响应中 | 停止生成 | 暂不启用语音（初版建议） | 允许编辑下一条文字草稿，不自动发送或插队 |
| 未登录、输入过长、附件处理未完成 | 禁用发送并说明原因 | 按实际语音可用性处理 | 不因为发送不可用就误变成空白麦克风模式 |

模式判断应使用“是否有内容”，发送可用性另行判断；不能只复用 `canSend` 决定图标。仅空格视为空白，只有附件也应进入发送模式。

听写与手动编辑：保留既有文字，把新语音追加至可追踪的插入区域；如支持光标插入，明确处理选区和合成输入。初版可在用户开始手动编辑时收尾停止听写，避免实时识别覆盖改动。无论选择哪种，都不能把全部草稿每次无条件覆盖。

长按水晶球和按钮入口共用同一听写会话。麦克风权限拒绝、来电/音频中断、切后台、关闭对话、切换对象时停止录音并保留可用草稿；不能让旧页面的识别结果写入新会话。无识别文字时恢复空白状态，不发送空消息。键盘、照片附件、长文本、动态字号、VoiceOver、深浅色和减少动态效果需一起验证。

按钮保持稳定尺寸和位置；发送时不跳动。停止生成与停止听写应有明确不同的无障碍标签。无背景的框内麦克风仍应提供约 44pt 的有效触控区域。

## 9. 建议实施顺序与验收

1. 会话与上下文基础：迁移旧通用历史，接入首页/物品/任务/设置，隔离草稿和请求；同时完成输入框按钮调整。
2. 工具一致性：为已有应用能力补齐模型工具和回执；设置可读可改，实体与操作可追溯。
3. 任务生命周期：完成、暂停、取消、规则修改；先修复通知“完成”和贪睡取消的现有缺口。
4. 多阶段调度：实现组合规则、预览、版本替换、持久化恢复，再验证本地执行边界和是否需要云端能力。

关键验收：从不同入口进入同一对象仍看到相同历史；不同对象不串草稿或确认；改名不丢会话；完成任务后不再收到原计划或贪睡通知；旧通知不能误执行新规则；断网时查看/完成本地任务不依赖模型；语音补充不覆盖打字；停止听写不自动发送；修改配置有真实回执且界面同步更新。

实际完成范围、边界与体验步骤以本文开头为准；测试记录见根目录 DEVELOPMENT_LOG.md。TestFlight 发布是独立步骤。
