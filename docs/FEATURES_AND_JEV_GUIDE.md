## 1. 基本工作方式

| 角色 | 负责 | 不负责 |
|---|---|---|
| 手机 | 保存全部资料（SwiftData 与本机文件），执行工具，校验参数和版本，保存待确认操作与执行回执，安排本地通知 | 理解复杂自然语言 |
| 主模型（云端，ChatGPT 订阅直连） | 理解请求、选择工具、整理提议、解释结果、写首页总览 | 直接写入资料；它的回答不等于操作成功 |
| Jev（可选） | 对给定条件与候选打分，辅助判断，见第 10 节 | 生成回答、授权操作、充当数据库 |
| 你 | 核对并确认修改 | — |

- **提议 → 确认 → 执行 → 回执**：库存、笔记、任务、设置及所有系统写入，模型只能提出待确认项；你点确认卡或说“确认 / 取消 / 确认第 2 项”后，手机才执行，并按提案编号保存逐项回执。确认时再次核对对象版本，界面上已改过的东西不会被旧卡片覆盖。模型没有“提交”工具。
- **本地存储不等于离线**：使用云模型时，相关消息、照片和工具查询结果会发给模型服务。健康数据的系统读取结果是例外，只在本机显示（第 7 节）。
- **没有常驻后台 AI**：模型只在你发消息或首页需要更新总览时调用；已确认的任务由手机按规则安排通知，不会每隔几分钟再问一次模型。
- 工具一共一百多个，按领域分在 `Butler/Services/Agent/*Tools.swift`。模型只能组合已实现的工具，不能凭一句话创造新的系统权限或执行能力。

## 2. 首页

从上到下：

1. **顶部栏**：左上角是今天的日期与星期（纯文字），点开月历面板，选一天就看那天的清单；右上角是“物品”和“管家与设置”两个图标。
2. **管家总览卡**：左上角问候与简短天气描述，更新状态靠整张卡片右上角。正文概括今天整体有哪几类安排、有没有前几天遗留的、这几天要提前准备什么，最后点出最该先处理的一件；不复述清单里已有的车次、钟点、地址。下方只居中保留直接处理那件事的按钮（如完成任务 / 稍后提醒 / 用完了 / 先放放），无须处理时不放按钮；不再有“其他”或详情入口，统一从底部输入回应。
3. **今日安排**：当天完整清单，不截断不折叠。任务行左侧圆圈点一下即完成，长按有“完成 / 30 分钟后再提醒 / 暂停提醒 / 取消任务 / 查看详情”。已完成的放在“已完成 N 件”小标题下仍可见。清单区域左右滑动逐日翻看过去和将来，今天时右侧留空；非今天时显示具体日期与星期，右侧有“回到今天”按钮。
4. **日程总览**：底部一行，副标题统计今天至周日的安排。

安排区不显示左右箭头，直接左右滑动卡片翻日；离开今天后显示“回到今天”按钮。顶部日期保持今天，安排标题标明正在浏览的日期。总览短清单不添加整屏底部占位，按实际内容限制滚动。

**总览怎么生成**：已登录时，模型读完全部在库物品、全部本地任务与规则、已确认笔记、家庭背景、最近 12 轮已完成对话（按页读取，每页最多 30 条或约 12 KB），以及已授权的系统日历和新鲜天气，再写总览。它只能用只读工具，不能修改任何东西。按钮效果限定在固定集合内并逐项校验；药品库存变化会再确认一次；“先放放”先让你选时长（1 小时、明早 9 点、3 天后 9 点、自选），只影响首页推荐，不改任务通知。

**什么时候刷新**：资料、设置、日历授权或天气变化时重新判断。结果缓存到模型给出的复查时间或当天午夜（取较早者）；同样资料不重复请求。下一次检查取资料自身的时间边界、午夜、天气获取 30 分钟后、天气观测 2 小时后中最早的一个。请求最长 90 秒，失败 10 分钟后才重试。另有系统后台刷新任务尽力提前更新，iOS 不保证运行时间。你开始操作卡片后，本轮可见内容锁定，新结果等你操作完再换。未登录、断网、超时或回复不合格时，显示手机本地拼出的句子和默认按钮。

**日程总览**：页面标题为“日程总览”。按日期分组的连续清单，默认定位今天，向上看过去、向下看未来，分段加载。右上角日历图标打开紧凑月历抽屉，选一天即收起并定位，可翻月和选择年月，标题旁可“回到今天”；无关闭叉号、无时间段筛选，抽屉按内容高度适配，定位后仍可前后连续浏览。每日提醒折叠在适用日期下；已完成记录保留但不计数；日历事件显示真实结束时间，跨天事件单列并注明完整起止。系统日历未开启、未授权或读取中会简短说明，不当作没有安排。

首页交互的设计约束见 `Butler/Views/Home/AGENTS.md`。

## 3. 对话

### 3.1 一张面板，按对象分会话

全 App 只有一张从底部升起的对话面板。不同入口打开不同会话，各自保存历史、摘要、草稿、照片、待确认项和阅读位置，互不串：

| 入口 | 会话 |
|---|---|
| 首页、日程总览、任务列表 | 通用对话 |
| 物品页 | 库存对话 |
| 具体物品批次 | 该批次自己的对话（改名不丢） |
| 具体任务 | 该任务自己的对话（完成、取消后保留） |
| 管家与设置 | 设置对话 |
| 某一天的日程 | 该日期的对话 |

首页底部输入携带打开时看到的整张提醒，仍使用通用对话和原有草稿；不是默认讨论快捷按钮指向的单个对象。旧的总览独立对话数据保留，但卡片不再提供“其他”入口。

账号、库存、笔记、任务和全局设置所有会话共享。每轮都读最新资料，旧聊天里的数量不能代替当前库存。通用对话里涉及某个物品或任务的轮次，会以引用方式出现在该物品/任务详情的“相关对话”里。历史完整保存，不截断；较早的部分由模型压缩成摘要供上下文使用，原文仍可检索。

### 3.2 输入

- **水晶球**：固定在页面底部。短按（不到 0.3 秒）打开当前页面对应的对话并聚焦输入框，面板全高；按住 0.3 秒开始说话，按下立即有连续触感，录音时两侧是真实音量声条，上滑进入红色区松手取消，松手整理后直接发送，面板停在约 3/4 高。10-07 视觉改为同一玻璃表面连续展开，轮廓与反射同步变化；取消区从圆条内部长出。此次流畅度仍待真机体验确认。设计约束见 `Butler/Design/AGENTS.md`（禁止环形进度圈等）。
- **输入栏**：左侧“＋”（拍照、相册、选择文件），右侧空白时是语音、有内容时是发送。输入栏里听写结束后保留文字，不自动发送。文字最多 8000 字，每条消息最多 4 张照片、每张不超过 4 MB。
- **语音识别**：默认苹果识别；可在设置里换成 OpenAI 兼容的文件转写或实时转写服务，见 [语音识别](SPEECH_RECOGNITION.md)。
- 发送前先把文字和照片完整保存到手机，保存失败不发送、不清空输入；回复失败时，如果你还没改过草稿，原文和照片会恢复回输入框。

### 3.3 回复与确认

- 回复逐步显示在同一个气泡里，Markdown（标题、列表、表格、代码块、链接）正常排版；只开放 http/https/mailto 链接，图片不自动加载。停止或断网时已显示的片段标为未完成保存在本机，不当作正式答案，也不自动重发。
- 列出物品时显示可点的清单卡（名称、数量、位置、临期状态和推荐理由），可能在解释文字之前先出现。点行打开详情；× 或说“去掉某样”只从清单去掉，不动库存。
- 待确认卡在下一句话后仍保留，切换页面、重启都还在。回复进行中卡片可见但按钮暂时不可用。每次确认生成独立执行记录，状态分为执行中、已完成、未完成、待核实、等你操作、收到系统回执；执行中途被打断，重新打开只恢复记录，不自动重做。
- 阅读历史时不会被新回复强行拉到底；输入区上方有“回到最新”。

### 3.4 未登录与断网

- 未登录时，“我有什么衣服”“冷藏里有什么”“螺丝刀放哪了”“什么快过期了”这类单一对象的查询由手机直接列出；已登录时一律交给模型，避免本地关键词误判。
- 断网时，在允许的会话里说一句定时提醒，手机会按本地解析先给出提醒提议，仍需你确认。
- 明确的“确认 / 取消 / 确认第几项”始终在手机本地处理，不需要模型。

### 3.5 Agent 能力基础优化（2026-10-15，已随 TestFlight 45 发布）

这一批改动着重让模型理解产品和修改对象，减少为了某种说法新增专门流程。

- **产品认知**：系统说明保留简短的产品概念，`get_product_guide` 可按主题查询详细边界和当前实际注册的工具。区分库存与购买、日期／时段安排与定时通知、本机保存与家庭同步／对方收到。目录只读，不读取个人资料，也不代表已经取得系统权限；已知如何执行时不用先查目录。
- **修改已有任务**：`propose_task_update` 按字段修改文字、单次日期／时段／钟点和家庭设置。未指定的字段保留；模型需提供查询到的任务编号和版本。重复、分段任务可以局部改文字或家人，修改时间规则仍使用完整计划，避免丢失原规则。
- **修改待确认事项**：`get_pending_changes` 返回可改字段、实际值及内容指纹；`revise_pending_change` 在原卡片上修改，保留编号、顺序及来源归属。支持任务、新增物品的名称／数量／单位／位置，以及现有库存数量或用完提案的数量更正。用户已手动修改、移除卡片，或库存版本已变化时，旧输入不会覆盖新内容。其他类型仍按对应工具替换指定提案。
- **家庭设置**：可见范围、负责人和通知对象分别表示不同选择。局部修改不隐式清空其他选择；冲突返回给模型核对。确认时重新检查相关成员是否仍在当前家庭。个人可见指创建者，不一定是当前操作者；空通知名单表示按产品默认提醒负责人或创建者，并非静音。
- **评估基线**：Debug 的 `AgentScenarioRunner` 使用真实工具循环和隔离的合成资料，覆盖模糊时间改口、库存数量更正、连续修改、只换负责人、拒绝地点许可及许可后仍须取得地点等六组多轮场景。判定依据为实际对象与状态，记录模型轮数、工具调用数和首个新建／修改提案的耗时。测试不读真实账户、不通知家人，也不触发首页刷新。真实模型入口需显式启用并注入模型。

验证：完整测试 832 项，831 项通过、1 项既有跳过；交叉审查修正后 32 项相关测试通过，Release 真机构建通过（未签名、未安装）。此轮未运行真实模型评估，不能据此宣称理解准确率或响应时间已提升。此阶段未实现统一的跨能力目标恢复或按需加载工具；后续工具并发见 3.6。所有实际业务修改仍需确认，Jev 开关行为保持原有约定。

### 3.6 Agent 等待时间优化（2026-10-15，已随 TestFlight 45 发布）

- **独立读取并行**：同一批明确安全的只读工具最多同时执行 3 个，每组最多包含 1 个库存 Jev 查询，回执仍按模型请求顺序返回。创建／修改提案、权限操作、刷新以及未知工具保持顺序执行，并使已有读取缓存失效。取消或失败不会继续执行后续修改。
- **减少重复读取**：仅在当前一次用户请求内复用完整、成功且仍有效的读取，包括符合条件的预取结果。资料、家庭权限、Jev 配置、静默重新载入或时间边界变化后失效；任务读取最多缓存 5 秒，其他读取最多 30 秒。不缓存失败、部分结果或需要实时反映的待确认内容；缓存命中不会延长原有效期。
- **减少重复 Jev 判断**：同一次用户请求中，完全相同的问题和候选资料可以复用有效判断，重叠请求合并等待。新增问题仍发送；错误、不完整结果不复用。新一轮对话、配置变化或关闭 Jev 后失效，不绕过原有审查和确认。
- **精简任务列表**：列表只附每项任务最近 3 条活动，同时标注历史总数及是否截断；按任务编号查询仍返回完整历史，实际存储不删减，时间规则、家庭设置和版本校验保留。
- **可观测性**：记录请求字节数、模型轮数、工具执行数、缓存命中、并发数量和首次提案准备耗时；这些诊断不记录用户正文或凭据。首次提案准备不等于界面已显示、用户已确认或任务已保存。

验证：完整测试 861 项，860 项通过、1 项既有跳过；补充静默重新载入失效检查后，最终 52 项定向测试全部通过，未签名 Release iOS 构建通过。合成工具负载中，每次读取模拟 40 毫秒延迟，3 项独立读取加 2 项重复读取由 208 毫秒／5 次执行降至 42 毫秒／3 次执行（前次运行 43 毫秒）；模型轮数仍为 3，使用脚本模型。100 项任务各 100 条历史的合成列表从 1,914,964 字节降至 126,164 字节。未测真实模型端到端延迟，不能把这些数字当成手机对话整体提速比例。模型及思考强度未调整。随后随提交 `7c37c15` 发布 TestFlight 1.0（45），云端 861/862 项通过、1 项既有跳过，内部／外部 test 组已可测试；未代用户在手机安装。

## 4. 物品

- 分类：食品、药品、日用品、衣物、数码家电、工具、其他物品。每个批次可记属性（颜色、尺码、材质、季节等）、用途标签、可用 / 待清洗 / 借出 / 维修状态和照片。耐用品不会因为只剩一件就提示补货，也不要求填有效期。
- 物品页：每件库存记录一张圆角卡片，展示照片或图标、名称、数量、类别、位置及日期状态，点击直接打开详情。顶部平时使用系统导航栏，右侧只显示搜索与更多；搜索时原位替换为输入框和取消，自动聚焦键盘并实时筛选，取消后恢复原栏；更多菜单里选择“分类 / 位置 / 到期”分组及“列表 / 网格”显示方式，两种偏好独立保存；相同名称的不同批次仍独立显示。无到期日期的数量型物品不显示“只记数量”分组；底部保留“已处理的物品”。卡片采用小缩略图，不为名称或缺省日期预留空行；大量物品用懒加载网格或列表，照片缩略图后台生成，大字体切换单列。
- 日期区分“包装有效期 / 预计到期 / 计划用完”。没说有效期时，部分能识别的食品会生成本地默认的“建议用完日期”，它不是包装有效期。
- 对话里可以新增、查询、改数量 / 位置 / 日期 / 跟踪方式、批量改位置和分类（每件一条待确认）、查变动历史、撤销最近一次符合条件的操作。详情页可手动编辑资料与照片。
- 新增购买仍保留独立批次，不与旧批次合并；“一盒鸡蛋”就是 1 盒，不猜成 10 个。

## 5. 任务与提醒

- 规则可组合：一次、每日、每周、每隔若干分钟（必须有次数或截止）、多阶段各自的起止与次数、全局截止，以及明确要求的“某时自动标记完成”。例如“连续三天提醒寄件，前两天每天 20 点，第三天 18 点起每十分钟一次，最多六次”。
- 确认卡用几句人话说明安排；完整规则在任务详情。修改保留任务编号并升级版本，旧通知不会改动新规则。
- 到提醒时间仍是未完成，首页显示“已到时间 · 待完成”；完成后停止后续提醒但保留记录。暂停、恢复、取消、重新打开、删除都可从详情、首页长按或对话进行；删除需要再确认，会移除操作记录但保留对话。
- 简单的每日/每周规则交给系统重复；复杂计划由手机预排近期通知，任务通知预算 40 条，超出时说明覆盖到哪一天并提示回 App 补排。长期不打开 App 不能保证无限执行复杂计划。
- 通知上的“完成”按钮可直接完成任务。

## 6. 天气

默认使用手机定位（首次打开天气时请求“使用期间”定位，不做后台定位），也可在天气面板或对话里切换城市。Apple WeatherKit 提供当前天气、最多48小时逐小时预报与未来7天预报，缓存半小时。首页左上角简短口语描述天气变化，影响已知出行时才在正文说明准备，不机械重复。目的地天气单独只读查询，不更改首页城市；只有整日预报时不猜具体时段，地点有歧义或读取失败时保持未知。旧描述在天气变化、过期或复查时间到达时停用。点开仍是温度、体感、风速、预警、未来几天和 Apple Weather 来源面板；模型不收到坐标。新天气表达和目的地查询尚待苹果端验收，不代表持续后台监控。

## 10. Jev：辅助判断

本节第 10.1–10.8 小节写于 2026-09-28（当时基线 `codex/jev-prefetch` / `93fe6da`），文中“本次新增”“这次修改”均指那次改动。2026-10-06 已对照代码确认：模型 `jev-1.13.0`，预取判断阈值 0.8 / 0.2，预取等待 1.5 秒，其他请求超时 8 秒，预取库存最多 40 个批次 / 约 12000 字节、笔记 20 条 / 约 8000 字节，相关性判断候选 2–30 个或无命中时全部库存不超过 60 个批次，均未变化。示例是预期处理方式，不是对真实模型输出的逐字保证。

### 10.1 主模型、手机和 Jev 分别做什么

| 角色 | 工作 | 不应混淆的边界 |
|---|---|---|
| 主模型 | 理解自然语言、整理购买清单、选择工具、解释结果和生成建议 | 不能直接把一句回答当成数据库写入成功 |
| 手机程序 | 查询数据库、验证参数、管理待确认操作、执行保存、返回结果 | 查询和加减计算本身不需要 Jev |
| Jev | 对指定条件和候选返回判断分值，如是否需要库存、是否指向某件物品 | 不是数据库、不是主要回答生成器，也不是操作授权者 |
| 用户 | 核对并确认对话提出的修改 | 模型提议或 Jev 通过都不代替用户确认 |

**需要查库存，不等于需要 Jev。**关闭 Jev 后，主模型和手机工具仍能完成业务，但会失去 Jev 提供的辅助判断。调用 Jev 也不保证判断正确。

库存等资料保存在手机；进行云模型对话时，相关消息、照片和工具结果会发送给主模型服务。Jev 请求会携带判断所需的原话、有限上下文或候选资料。因此“本地存储”不等于“全部离线处理”。Jev 密钥存放在系统钥匙串。

### 10.2 当前什么时候会调用 Jev

前提是已配置密钥并开启“启用 Jev”。当前模型标识为 `jev-1.13.0`；这次修改没有更换模型。

#### 10.2.1 回答前：提前准备查询资料（本次新增）

“提前准备查询资料”开启时，大多数非空文字请求会先经过 Jev。空消息、代码列出的简单问候、带照片请求、Jev 不可用等情况直接跳过。

一次请求同时判断三个条件：

1. 是否属于支持的只读场景？
2. 是否需要当前库存？
3. 是否需要已保存的个人偏好或习惯？

支持的范围是库存数量、位置、有哪些物品、到期情况，以及结合库存与偏好的饮食或采购建议。新增、修改、删除、消耗、提醒、历史回顾、照片处理，以及混合这些操作的请求均不属于当前预取范围。单独的偏好查询也不因需要笔记就必然进入预取。

若判断足够明确，手机读取选中的数据源，作为真实工具结果交给主模型。主模型资料足够时可以直接回答，不足时仍可补查。

```text
用户问题 → Jev 判断资料需求 → 手机读取选中的资料 → 主模型回答或补查
```

当前预取是选择“库存/笔记”数据源，不是让 Jev 提取购买清单或生成精确查询词。库存最多返回 40 个批次、约 12,000 字节预算；笔记最多 20 条、约 8,000 字节预算。结果附带来源、查询时间、范围和完整性标记。

判断分值达到 0.8 才视为明确肯定，0.2 以下视为明确否定，中间区间回退；这只是程序阈值，不代表经实测校准的准确率。预取判断等待期限为 1.5 秒；不确定、失败或超时后照常交给主模型查询。这个期限不代表整个回答，也不代表所有 Jev 调用都只等 1.5 秒。Jev 客户端其他调用的请求超时配置为 8 秒。

**新增购买当前仍可能先调用一次 Jev，然后判定不预取。尚未实现“明确购买请求直接绕过这次判断”。**

#### 10.2.2 查询过程中：相关性判断（原有能力）

普通库存工具首先进行名称、品牌、位置的关键词匹配。

- 关键词命中 2–30 个候选时，可请 Jev 打分排序，保留关键词命中结果。
- 关键词没有命中且当前库存不超过 60 个批次时，可请 Jev 从候选池辅助寻找相关项。
- 查询全部库存时不进行这次相关性判断；此次预取也不会再次进行相关性判断。
- 语义筛选可能漏项，不能据此证明“家里没有”。

这是有条件的候选判断，不是已经建立了完整的语义搜索或商品规格识别系统。

#### 10.2.3 提出修改时：操作核对（原有能力）

- 新增物品匹配已有同名或关联商品时，核对是否真的又新买，而非纠正旧记录。
- 文本请求的提议里有包装有效期时，核对日期是否有用户原话依据。
- 修改已有批次时，核对目标物品；部分数量修改也核对“用掉多少”和“还剩多少”的含义。
- 主模型也可以主动调用 `judge_with_jev` 对候选做条件判断。

新增没有匹配的旧记录、也没有包装日期时，新增核对可能不发起 Jev 请求。它并不逐项全面审计数量、单位、品牌和包装规格。

Jev 提出疑问时，工具返回 `needs_review`，让主模型修正或追问。若主模型坚持原提议并再次提出相同操作，代码允许显示带疑问的确认卡片，由用户决定；这不是绝对阻断。Jev 失败也会回退，不应把未检查称为“检查通过”。

### 10.3 购买四样东西时的实际流程

示例原话：“今天刚买了，一包方便面，大袋装的，一袋火腿，一把青菜，一盒鸡蛋。”

1. 若预取开启，Jev 先判断；正常识别为新增后，不预取库存或偏好。
2. 主模型理解原话，调用 `propose_add_items`，预期形成以下提议。

| 物品 | 数量和单位 | 未知信息 |
|---|---|---|
| 方便面（大袋装） | 1 包 | 袋内小包数、重量、品牌 |
| 火腿 | 1 袋 | 根数、重量、具体种类 |
| 青菜 | 1 把 | 重量、品种 |
| 鸡蛋 | 1 盒 | 盒内枚数 |

3. 手机校验格式，查找已有商品关联，按上述条件调用 Jev 核对。
4. 显示待确认卡片，此时尚未入库。
5. 用户确认后，手机执行保存并生成回执。

主模型也可能按请求先调用查询工具；当前没有强制“每次新增都先完整查询匹配库存并展示合计”的业务流程。

当前没有独立的包装规格字段。“大袋装”通常要保留在名称中，仍需核对模型是否正确保留。一盒鸡蛋就是 1 盒，不能自动猜成 10 个；之后说“吃了 2 个”时，不能在不知道盒内数量的情况下直接换算。

未提供存放位置和包装有效期时，提议应留空。保存阶段对部分能识别品类的食物，若没有日期，手机可能生成本地默认的“建议用完日期”。它不是包装有效期，也不是 Jev 推算的保质期。当前新增路径的 `purchasedAt` 写入为 nil，不应因为说了“今天刚买”就宣称已经保存了明确购买日期。

### 10.4 为什么新增时也可能需要查旧库存

本次讨论倾向于：新增时简短说明相关库存变化，比只说“保存好了”更有用。但合计必须来自真实查询，并能比较单位和规格。

| 已有 | 新买 | 建议表达 |
|---|---|---|
| 同规格火腿 2 袋 | 1 袋 | 确认前：“本次新增 1 袋，确认后共 3 袋。”保存成功后：“已记好，现在共 3 袋。” |
| 火腿 3 根 | 1 袋，根数未知 | “原有 3 根，本次新增 1 袋。”不强行换算 |
| 已开封半袋 | 未开封 1 袋 | 若数据能准确表达，应分别说明；当前数量为整数，半袋不是已支持的完整建模能力 |
| 未查到明确匹配 | 1 袋 | 说明本次新增，不把模糊匹配或部分结果当成不存在 |

用户看到的合计与数据库批次是两件事。界面可以汇总，新增购买仍保留独立批次，避免混淆日期。仅凭同名不能证明品牌、规格、单位都一致。

**当前尚未实现的完整改进流程：**主模型提取清单 → 手机批量查相关库存 → 结合匹配结果形成新增与合计提议 → 必要时 Jev 核对 → 用户确认。不能把这段建议描述为已上线功能。

### 10.5 到底什么时候值得用 Jev

| 情况 | 设计建议，不等同于当前调用策略 |
|---|---|
| 明确新买 1 袋，同规格旧库存 2 袋 | 通常无需 Jev；主模型提取，手机查询和计算即可 |
| “火腿是两袋” | 可辅助判断纠正、剩余还是新增；不确定则追问 |
| “吃掉了那个火腿”，有多个不同候选 | 可辅助判断指向哪件，不能用分值掩盖歧义 |
| 提议出现未说过的日期 | 可核对原话依据，不能替代日期规则和用户确认 |
| “结合库存和口味，今晚吃什么” | 可提前判断资料需求，争取省掉主模型工具往返 |
| 已确认同单位数量相加 | 程序直接计算，无需 Jev |

Jev 的两项核心价值是：提前判断资料需求以争取减少等待，以及对有歧义的含义/候选做辅助核对。是否启用某处判断，应以实际延迟、错误率和请求成本衡量，不以调用次数越多越好。

### 10.6 这次修改前后有何变化

修改前已有部分相关性判断和修改核对。此次新增的是回答前的资料预取、独立开关，以及查询范围和完整性提示；未更换 Jev 模型，也未让 Jev 直接写数据库。

```text
原流程：问题 → 主模型要求查询 → 手机执行（部分查询可调用 Jev）→ 主模型回答
新增预取命中：问题 → Jev 判断 → 手机预取 → 主模型直接回答或补查
```

潜在收益是减少主模型查询往返。代价是新增 Jev 请求耗时与用量，预取资料也会占用主模型输入。超时、不确定、不适用或资料不足时可能不加速，甚至更慢；不能保证更省钱或更准确。

### 10.7 如何在手机比较差异

在设置的“Jev 条件判断”里配置有效密钥，保持“启用 Jev”打开，仅切换“提前准备查询资料”。关闭整个 Jev 会同时关闭原有辅助判断，不能单独衡量此次预取改动。

准备固定的虚构库存和偏好，例如鸡蛋、牛奶、青菜及“不吃辣”。在相同模型、网络和资料下，使用新对话，交替开关重复以下问题：

- 家里还剩多少鸡蛋？
- 牛奶放在哪里？
- 哪些东西快过期了？
- 按我的口味，用现有食材推荐晚餐。
- 刚买了一袋火腿。（用于观察不适用预取时的额外成本）

每次记录：开关状态、从发送到有用答案的时间、完整回答时间、事实是否准确、偏好是否遵守、是否合理补查或追问。比较多次结果，不用单次快慢下结论。

“Jev 请求尝试次数”是本次管家载入期间的尝试数，包含失败，不是计费单；开关不会清零，也不能单凭次数确认预取成功。Debug 自动对照测试入口不等于这次预取的完整真实服务性能评估。
